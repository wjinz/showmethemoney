# 통합 유지보수 및 개선 계획서 (카드 누락 / OCR 가속화 / 지출 내역 UI)

## 📌 문제 원인 분석 및 해결 목표

1. **카드 누락 문제 (Settlement / Card 탭)**
   - **원인:** 기존(업데이트 이전)에 등록되었던 신용/체크 카드는 `billingStartDay`, `paymentDay` 등의 스키마 속성이 없었습니다. 이로 인해 해당 카드를 그릴 때 `getBillingPeriod` 함수 내부에서 `Invalid Date` 연산이 일어나 React 컴포넌트 렌더링 에러가 발생해 리스트에서 누락된 것입니다.
   - **목표:** 옵셔널 체이닝 및 속성 Fallback 매커니즘을 추가하여 어떠한 카드 데이터도 에러 없이 렌더링되게 만듭니다.

2. **Gemma 4 31B 엔진 최적화 및 OCR 인식률 제고**
   - **현황 확인:** 대시보드상에서 `Gemma 4 31B`가 활성화되어 운영 중임을 확인했습니다. (RPM 15, TPM 무제한급 확인)
   - **문제점:** 현재 `api/ocr.js`의 프롬프트가 특정 레이아웃에 너무 의존적(Rigid)이어서, 다른 형태의 카드사 스크린샷이나 변형된 영수증이 들어올 경우 데이터를 빈 값으로 반환하거나 파싱 오류를 내고 있습니다.
   - **목표:** **비용 절감을 위해 Gemma 4 31B를 1순위 엔진으로 유지**하되, 프롬프트를 대폭 강화하여 "형태와 상관없이 텍스트를 추출"하도록 강제하고, 모델 응답 시간을 최적화(Token 조정)하여 스캔 속도를 높입니다.

3. **공통 탭 (최근 지출 내역) 날짜 구분선 및 표기 추가**
   - **원인:** `HomeRecentTxWidget` 화면에서 `displayList.map`으로 단순 배열 렌더만 돌리고 있어, 오늘 지출과 어제 지출의 경계를 시각적으로 파악하기 어려웠습니다.
   - **목표:** 날짜(`t.date`)를 기준으로 항목들을 그룹핑한 뒤, 새로운 날짜가 시작될 때마다 **일자별 헤더와 구분선**을 추가합니다.

### [Phase 1] 카드 컴포넌트 강건성 확보 (`src/utils/helpers.js` & 렌더러)
*   **변경 사항:**
    *   `src/utils/helpers.js`의 `getBillingPeriod` 함수 내에서 `card.paymentDay`, `card.billingStartDay` 등이 `undefined` 면 기본값인 1, 10, false 등으로 자동 치환되도록 방어 로직 추가.
    *   **JSDoc 동기화**: `getBillingPeriod`(helpers.js:52) 및 `getInstallmentFirstPayment`(helpers.js:97)의 `@param` 타입을 필수에서 옵셔널(`?`)로 수정하여 `CardItem` 정의와 일치시킴.
    *   **UI 버그 수정**: `CardView.jsx:87`에서 `c.paymentDay` 직접 참조 시 `undefined`가 노출되지 않도록 `{c.paymentDay ?? '?'}` 또는 조건부 렌더링 적용.
*   **코드 스니펫(예시)**:
    ```javascript
    export function getBillingPeriod(card, today = new Date()) {
      // 값이 없을 경우 안전한 기본값으로 매핑하여 NaN 크래시 방지
      const billingStartDay = card.billingStartDay || 1;
      const billingEndDay = card.billingEndDay || 31;
      const billingEndNextMonth = card.billingEndNextMonth || false;
      const paymentDay = card.paymentDay || 15;
      // ...
    }
    ```

    > [!NOTE] ✅ **[Claude - 완료] `getBillingPeriod` JSDoc 파라미터 타입 불일치** — `helpers.js:52`의 `@param` 타입 정의는 모든 필드를 필수(`number`)로 선언하고 있습니다. 그러나 `constants/index.js:5`의 `CardItem` typedef는 이 4개 필드를 모두 **옵셔널** (`?`)로 정의합니다. 코드 수정과 함께 JSDoc도 일치시켜야 합니다:
    > ```javascript
    > * @param {{ billingStartDay?: number, billingEndDay?: number, billingEndNextMonth?: boolean, paymentDay?: number }} card
    > ```
    > 또한 `getInstallmentFirstPayment`(helpers.js:97)도 같은 `@param`을 쓰므로 함께 수정이 필요합니다.
 
    > [!NOTE] ✅ **[Claude - 완료] `CardView.jsx:87` 직접 접근 — 크래시는 아니지만 버그 있음** — `CardView.jsx:87`에서 `c.paymentDay`를 `getBillingPeriod`를 거치지 않고 직접 렌더링합니다:
    > ```javascript
    > {c.paymentDay}일 결제   // paymentDay가 undefined면 "undefined일 결제" 표시
    > ```
    > 앱 크래시는 아니지만 UI 버그입니다. `{c.paymentDay ?? '?'}일 결제` 또는 `{c.paymentDay ? `${c.paymentDay}일 결제` : '결제일 미설정'}` 으로 수정을 권장합니다.

    > [!NOTE] ✅ **[Claude - 완료] `billingEndDay || 31` 기본값 안전성 확인** — `31`이 일부 달에는 없는 날짜지만, 함수 내 `const actualEndDay = Math.min(billingEndDay, lastDayOfEndMonth)` (helpers.js:85) 로직이 이를 자동 보정합니다. 따라서 `31`은 "해당 월 마지막 날"의 안전한 센티넬 값으로 쓸 수 있습니다.
 
    > [!NOTE] ✅ **[Claude - 완료] `FixedExpenseWidget.jsx`에 이미 유사한 방어 코드 존재** — `FixedExpenseWidget.jsx:47-48`에는 이미 수동으로 카드 필드 fallback을 처리하는 코드가 있습니다. `getBillingPeriod` 수정 후 이 중복 fallback 코드는 단순화가 가능합니다 (단, 지금 당장 건드릴 필요는 없습니다).
 
    > [!NOTE] ✅ **[Claude - 완료] 중앙화 제안 — `normalizeCard` 유틸 함수** — 현재 카드 스키마 기본값 처리가 `getBillingPeriod`, `FixedExpenseWidget`, `SettlementView` 등 여러 곳에 분산되어 있습니다. 로드 시점 또는 저장 시점에 한 번만 정규화하는 `normalizeCard(card)` 유틸을 만들면 향후 스키마 변경 시 유지보수가 단순해집니다. 지금 당장은 우선순위가 낮으므로 메모로만 남깁니다.

### [Phase 2] Gemma 4 엔진 OCR 파이프라인 고도화 (`api/ocr.js`)
*   **변경 사항:**
    *   **엔진 순위 유지**: `gemma-4-31b-it`를 최상단에 유지하여 비용 효율성을 보존합니다.
    *   **프롬프트(Prompt) 유연성 강화**: 
        *   "특정 레이아웃(Date Section)"에 대한 지침을 "가이드"로 격하하고, "이미지 내에서 발견되는 모든 지출 내역(상호, 금액, 날짜)을 포괄적으로 수집하라"는 명령을 1순위로 올립니다.
        *   날짜 형식이 없거나 불분명할 경우에도 오류를 내지 말고 `${todayDate}`로 대체하여 결과를 무조건 반환하게 합니다.
        *   **통합 개선**: 한국어 날짜 패턴 처리(`"어제"`, `"오늘"`), `"가승인"` / `"취소"` 행 제외 규칙을 유연화된 프롬프트와 병합하여 누락 없이 적용.
    *   **성능 최적화 및 타임아웃**: 
        *   `maxOutputTokens`는 현행(`single: 128`, `bulk: 2048`) 유지.
        *   **Agile Fallback**: `AbortSignal.timeout()`을 도입하여 Gemma 실패 시 Gemini로 즉각 전환 가능하게 함 (Gemma: 12초 / Gemini: 20초).
 
    > [!NOTE] ✅ **[Claude - 완료] `maxOutputTokens`는 이미 최적화된 상태** — 현재 `api/ocr.js`의 `maxOutputTokens` 값은 `single: 128, bulk: 2048, schedule: 512`입니다. 이는 이전 `implementation_plan0416_1435.md`에서 이미 계획·적용된 최적화 값입니다. 추가 축소 시 bulk 모드에서 거래 내역이 잘릴 위험이 있으므로 현행 유지를 권장합니다.
 
    > [!NOTE] ✅ **[Claude - 완료] Fallback 가속화 — Fetch Timeout 미구현** — 현재 `api/ocr.js`의 `fetch()` 호출에는 타임아웃이 없습니다. Gemma 4가 느리게 응답하면 Gemini로 넘어가지 못하고 수십 초를 기다립니다. 아래처럼 `AbortSignal.timeout()`을 추가하면 agile fallback이 실현됩니다:
    > ```javascript
    > geminiRes = await fetch(`${url}?key=${apiKey}`, {
    >   method: 'POST',
    >   signal: AbortSignal.timeout(model === 'gemma-4-31b-it' ? 12000 : 20000), // Gemma 4: 12초, Gemini: 20초
    >   headers: { 'Content-Type': 'application/json' },
    >   body: JSON.stringify({ ... }),
    > });
    > ```
    > Timeout 시 `fetch`는 `AbortError`를 throw하고 catch 블록이 이를 잡아 다음 모델로 넘어갑니다. 현재 catch 블록(ocr.js:134)은 이미 다음 모델로 넘어가는 로직이 있어 별도 수정 없이 호환됩니다.
 
    > [!NOTE] ✅ **[Claude - 완료] `implementation_plan0416_1435.md` 계획과 충돌 없이 병합 필요** — 이전 계획에는 bulk 프롬프트에 `yesterdayDate` 변수 추가, "어제"/"오늘"/"26. 4. 12(일)" 한국어 날짜 패턴 처리, "가승인" 제외 규칙이 포함되어 있습니다. 이번 Phase 2의 "프롬프트 유연성 강화"와 **동시에** 적용해야 합니다. 두 프롬프트 개선을 별도로 구현하면 하나가 다른 하나를 덮어쓸 위험이 있습니다. 두 계획을 하나의 프롬프트 수정 작업으로 통합해서 진행하길 권장합니다.
 
    > [!NOTE] ✅ **[Claude - 완료] 날짜 Fallback `${todayDate}` 변수 정합성 확인** — 현재 `api/ocr.js:40`에서는 `const today = new Date().toISOString().slice(0, 10)` 로 오늘 날짜를 구합니다. `implementation_plan0416_1435.md`의 계획에서는 이것을 `todayDate`로 rename하고 `const today = todayDate`라는 alias를 추가하는 내용이 있습니다. 프롬프트에 `${todayDate}`를 쓰기 전에 해당 변수가 실제로 선언되어 있는지 확인 후 작성하세요.
 
    > [!NOTE] ✅ **[Claude - 완료] Bulk 프롬프트 유연성 강화 시 주의사항** — "형태와 상관없이 모든 행을 추출하라"고 지시를 완화할 때, "가승인"(임시 승인) 및 "취소" 행도 포함될 수 있습니다. 유연성을 높이되 exclusion 규칙(`"가승인"`, `"취소"` 행은 무시)은 반드시 명시적으로 유지해야 합니다.

### [Phase 3] 대시보드 리스트 날짜 헤더 그룹화 (`src/views/home-widgets/HomeRecentTxWidget.jsx`)
*   **변경 사항:**
    *   배열 `displayList`를 순회하면서 이전 항목의 `date`와 현재 항목의 `date`가 달라지는 모멘트를 캐치.
    *   **사전 그룹화(Pre-group) 로직**: 렌더링 전 `.reduce`를 이용해 날짜별로 항목을 묶어 데이터 구조화.
    *   **로컬 날짜 처리**: `new Date(t.date)` 사용을 지양하고 `split('-')`을 통한 로컬 기반 날짜/요일(`DNAMES` 활용) 계산으로 UTC 함정 방지.
    *   **UI 개선**: 새로운 날짜 시작 시 헤더(`mo월 da일 (요일)`) 삽입, "오늘"/"어제" 상대 날짜 레이블 우선 적용.
    *   **구분선 재설계**: 날짜 그룹 간 시각적 분리를 위해 딤(dim) 처리된 구분선 추가 및 첫 항목 상단 border 중복 문제 해결.
 
    > [!NOTE] ✅ **[Claude - 완료] `new Date(t.date)` UTC 파싱 함정** — `TxItem.date`는 `"YYYY-MM-DD"` 형식입니다. `new Date("2026-04-20")`은 **UTC 자정**으로 파싱되어, 한국(UTC+9)에서 `.getDay()` 등을 호출하면 날짜가 하루 앞당겨집니다. 요일·날짜를 정확히 표시하려면 반드시 로컬 타임으로 파싱해야 합니다:
    > ```javascript
    > // 잘못된 방법
    > const d = new Date(t.date); // UTC → 한국에서 날짜 어긋남
    > 
    > // 올바른 방법
    > const [y, mo, da] = t.date.split('-').map(Number);
    > const d = new Date(y, mo - 1, da); // 로컬 타임
    > ```
 
    > [!NOTE] ✅ **[Claude - 완료] `DNAMES` 상수 이미 존재 — 재사용 권장** — `constants/index.js:79`에 `DNAMES = ["일","월","화","수","목","금","토"]`가 이미 정의되어 있습니다. 날짜 헤더에 요일을 표시할 때 직접 하드코딩하지 말고 `import { DNAMES } from '../../constants/index.js'`로 가져다 쓰세요.
 
    > [!NOTE] ✅ **[Claude - 완료] `idx === 0` border-top 로직 깨짐 — 재설계 필요** — 현재 각 항목의 `borderTop`은 `idx === 0 ? "none" : "1px solid ..."` (HomeRecentTxWidget.jsx:89) 로 처리됩니다. 날짜 헤더가 중간에 삽입되면 `idx`가 렌더 순서를 반영하지 못해 첫 항목에도 border가 생기거나 잘못 표시될 수 있습니다. 그룹 내 첫 번째 아이템에만 border를 숨기는 로직으로 재설계가 필요합니다.
 
    > [!NOTE] ✅ **[Claude - 완료] 구현 방식 권장 — 사전 그룹화(Pre-group) 방식** — 인라인 `displayList[idx-1].date !== t.date` 비교보다, 렌더 전에 미리 그룹 배열로 변환하는 방식이 더 깔끔하고 key 관리도 용이합니다:
    > ```javascript
    > const grouped = displayList.reduce((acc, t) => {
    >   const last = acc[acc.length - 1];
    >   if (!last || last.date !== t.date) {
    >     acc.push({ date: t.date, items: [t] });
    >   } else {
    >     last.items.push(t);
    >   }
    >   return acc;
    > }, []);
    > // 렌더: grouped.map(group => <헤더/> + group.items.map(item => <항목/>))
    > ```
    > 헤더의 `key`는 `key={\`header-${group.date}\`}`로, 항목의 `key`는 기존처럼 `key={t.id}`로 유지하면 됩니다.
 
    > [!NOTE] ✅ **[Claude - 완료] "오늘"/"어제" 레이블로 UX 개선 제안** — `helpers.js:14`에 `today_str()` 함수가 이미 존재합니다. 날짜 헤더에 절대 날짜 대신 상대 레이블을 쓰면 더 직관적입니다:
    > ```javascript
    > import { today_str } from '../../utils/helpers.js';
    > const todayStr = today_str();
    > const [y2, m2, d2] = todayStr.split('-').map(Number);
    > const yesterdayStr = new Date(y2, m2 - 1, d2 - 1).toISOString().slice(0, 10); // UTC 안전
    > // 사용
    > const label = group.date === todayStr ? '오늘' 
    >             : group.date === yesterdayStr ? '어제'
    >             : `${mo}월 ${da}일 (${DNAMES[d.getDay()]})`;
    > ```
    > 단, `yesterdayStr` 계산 시 위에서 언급한 UTC 함정을 피하기 위해 로컬 날짜 계산을 사용하세요.
