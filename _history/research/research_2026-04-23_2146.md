# Research — 프로젝트 전체 구조 및 기능 인벤토리 (2026-04-23 21:46)

본 문서는 `어플개발_우진지연 budget` 전체 파일을 재조사한 결과로,
`src/` 모듈형 개발 베이스와 현재 배포본 `index.html`(단일 HTML) 사이의
기능 격차를 정량화하고, 누락 기능의 이식 전략 및 구조 개편안을 제시한다.

## 1. 프로젝트 이중 구조 개요

| 축 | `src/` 계열 (모듈형) | `index.html` (현재 프로덕션) |
|---|---|---|
| 빌드 | Vite + React 18 + JSX | CDN React 18 + Babel Standalone (`text/babel`) |
| 엔트리 | `src/main.jsx` → `App.jsx` | 단일 HTML 내 `<script type="text/babel">` |
| 상태 | `BudgetContext` + `kidsStore(Zustand)` | 전역 `useState` + `BudgetCtx` 일부 |
| DB | Supabase RDB (transactions RDB + household_data JSONB + sos_requests + kids_*) | Supabase Channel Broadcast 만 사용 |
| Realtime | `postgres_changes` (INSERT/UPDATE/DELETE) | Broadcast 채널 (sync_tx / sync_notes) |
| AI | `/api/nudge`, `/api/budget-ai`, `/api/kids-coach`, `/api/ocr` | `/api/nudge` 일부, OCR은 `alert` 플레이스홀더 |
| 저장 | DB 우선 + `offlineQueue(localStorage)` + `offlineIDB(IndexedDB)` | localStorage 14키 (네임스페이스 `smtm_*`) |
| 라우팅 | `App.jsx` view 상태 11종 | view 상태 8종 |
| 테마 | dark / light / oldschool + `data-theme`(joint/private/kids) | 다크톤 단일 |

| URL | `https://showmethemoney-eta.vercel.app` | 동일 |

## 4. Supabase 스키마 (`supabase_setup.sql` 기반)

```
household_data (
  household_id uuid PK,
  data jsonb,        -- plan, budgets, names, fixed, install, cards, settlements, assets, taxConfig
  updated_at timestamptz
);

transactions (
  id bigserial PK,
  household_id uuid FK,
  date date, amount int, cat text, memo text,
  who text, pay_method text, card_id text,
  type text, is_private bool, kid_id uuid,
  created_at timestamptz
);

sos_requests (
  id bigserial PK,
  household_id uuid, requester text, amount int,
  reason text, repay_plan text,
  status text,        -- pending | approved | rejected | resolved
  created_at, resolved_at
);
-- trg_sos_approved: status='approved' → transactions INSERT 자동

kids_profiles (
  id uuid PK, household_id uuid FK,
  name text, avatar text,
  goal_label text, goal_amount int, saved_amount int
);

kids_missions (
  id uuid PK, kid_id uuid FK,
  title text, reward_amount int,
  status text,  -- pending | done | rewarded
  created_at, completed_at, rewarded_at
);
```

RPC: `get_monthly_total_expenses`, `increment_kid_savings`, `complete_and_reward_mission`.
RLS: household_id 기반 격리.

## 6. 이식 우선순위와 단일 HTML 제약

### 6.1 우선순위 분류

**P0 (가계부의 본질적 결손)**
- 카테고리 9종 예산 (`smtm_budget` 구조 전환 + 마이그레이션)
- OCR 단일/벌크 + ReceiptSplitter
- `is_private` 블라인드 로직
- 할부(`InstallItem`) + 카드 결제주기
- SOS를 RDB 기반으로 승격 + 트리거 승인 → tx 자동 INSERT

**P1 (고부가가치)**
- AI 3종 (Nudge KV 캐시, Budget, Kids) 연동
- 연간 이벤트 / 목표 / 저축 타깃 (`Plan`)
- 자산 (AssetView)
- Kids Mode 전체

**P2 (관리/안정성)**
- Admin + BugReport
- 오프라인 큐 (최소 localStorage 단계) + 디바운스 저장 + 지수 백오프
- 데이터 임포트 (엑셀 xlsx)
- Realtime을 postgres_changes로 전환

**P3 (UX 고도화)**
- 위젯 대시보드 (react-grid-layout)
- 3테마 (oldschool 포함)
- PWA Share Target
- QuickEntrySheet 빠른 입력 칩 + FrequentPattern
- ScheduleScanSheet

### 6.2 단일 HTML의 구조적 제약

| 제약 | 영향 |
|---|---|
| 빌드 없음 (CDN + Babel in-browser) | 최초 로드 시 Babel 파싱 비용, 프로덕션 성능 저하 |
| JSX 전역 스코프 | 컴포넌트 수 증가 시 이름 충돌/가독성 문제 |
| 번들러 부재 | tree-shaking 없음, lucide 아이콘 1개도 전체 로드 |
| react-grid-layout | CSS 필수 (CDN 가능하지만 충돌 가능) |
| Framer Motion | CDN ESM은 되지만 Babel+ESM 혼용 난이도 상 |
| Zustand | CDN ESM 필요, useState와 이중 관리 시 혼란 |
| SheetJS | CDN 가능 (약 1.2MB 추가) |
| Service Worker | `/sw.js` 별도 배포 필요 |
| 코드 분할 없음 | 기능 전부 이식 시 5000줄 이상으로 비대화 예상 |

## 7. 구조 개편 옵션

### 옵션 A — 현 단일 HTML 유지, 증분 이식

- 장점: 배포 단순, 현재 URL/Vercel 그대로, 학습비용 최소
- 단점: 파일 비대화 (5000줄+), 디버깅 난이도 상승, 성능 회귀
- 적합: P0~P1까지만 이식하고 멈출 계획일 때
- 예상 최종 라인 수: 4500~5500줄

### 옵션 B — Vite 프로젝트로 복귀 (`src/` 기반) [권장]

- 장점: 기작성 `src/` 코드 95% 재활용, 기능 회복 최단 경로,
  tree-shaking/lazy loading/Realtime 고급 기능 복원 용이
- 단점: 배포 산출물 변경(`.vercel/output/static/index.html` → Vite build),
  HTML에만 있던 UX 뉘앙스 재이식 필요 (1일 이내)
- 적합: P0~P3 전부 이식 예정
- 작업량: 1~2일 (구조 복원만)

### 옵션 C — 하이브리드 (HTML 로더 + ES 모듈 분할)

- `index.html`은 골격/테마/Supabase 초기화만 담당
- 기능 단위를 `js/views/*.js`, `js/utils/*.js`로 분리, `<script type="module">` 로드

- 장점: 빌드 없이 모듈 분할
- 단점: JSX 없으면 개발 속도 급락, htm 학습비용

## 10. 결론 요약

현재 `index.html`은 `src/` 풀기능의 약 20~25% 수준만 구현.
HANDOVER_V5의 "P0~P6 완료"는 `index.html` 내부 뼈대 완성이지,
`src/`가 보유한 **24개 위젯·4종 AI·Kids/Asset/Tax/Install·오프라인 큐·Migration·3테마** 등의
차별 기능은 이전되지 않았음.

가장 효율적인 경로는 **옵션 B — Vite 복귀**.
`src/`를 프로덕션으로 재채택하고, `index.html`에서 다듬어진 UX 뉘앙스만
해당 뷰 컴포넌트로 역이식. 실작업은 기능 구현이 아니라
**DB 스키마 확인 + 환경변수 + 빌드 설정 복구**가 중심이 되며,
7일 내 전체 기능 복원이 가능.

### 🔴 필수 수정 및 인지 사항
1. **Gemma 4 모델 사용 목적 명확화 (비용 절감)**
   - API 연동 시 Gemma 4 등 경량 모델 파이프라인을 구축했던 핵심 이유는 오직 **"비용(Cost) 문제"** 때문임을 확실히 인지해야 합니다. 가계부 앱 특성상 영수증 다중 스캔 및 AI 넛지 호출 빈도가 높으므로, 고성능/고비용 모델 대신 API 호출 비용을 극단적으로 낮출 수 있는 현재의 모델 조합을 무조건 유지해야 합니다.
2. **3가지 테마 시스템 구현 폐기**
   - 기존 `src/` 설계에 존재하던 다크(Dark), 라이트(Light), 올드스쿨(Oldschool) 3종 테마 시스템은 **불필요하므로 구현하지 않습니다.** 개발 및 유지보수 리소스만 낭비될 뿐입니다. (기존 계획의 M5 단계에서 테마 복원 작업은 삭제합니다.)
3. **현재 디자인 레이아웃 및 형태 엄격 유지**
   - 옵션 B(Vite 기반 `src/` 복귀)를 채택하여 백엔드/상태 관리 로직을 복원하더라도, **디자인은 지금 `index.html`에 구현된 레이아웃과 형태를 100% 동일하게 유지한 상태로 진행**되어야 합니다. 기능 연동을 핑계로 기존 디자인 뉘앙스나 CSS 구조를 망가뜨리는 일은 유의해서 방지해야 합니다.

### 💡 추가 아이디어 및 제안
1. **'디자인 우선' 하이브리드 이식 전략**
   - `src/`의 기존 컴포넌트를 살리려다 UI가 꼬이는 것을 막기 위해, 현재 배포된 `index.html`의 뷰(View) 단위 JSX 코드를 그대로 `src/views/`로 복사-붙여넣기 한 뒤, 그 위에 상태 관리(BudgetContext)와 API 연동 로직만 주입하는 방식(Top-Down)을 강력히 권장합니다.
