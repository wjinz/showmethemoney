## 2. 핵심 모듈 및 아키텍처 분석

### 2.1 데이터 흐름 및 동기화 (Data Sync)
- **실시간성**: `src/utils/supabase.js`에서 Supabase의 Postgres Changes를 구독하여, 한 사용자가 데이터를 수정하면 파트너의 화면에도 즉시 반영됩니다.
- **연도별 데이터 분리**: 대량의 지출 내역(`tx`) 성능을 위해 `tx_YYYY` 키를 사용하여 연도별로 데이터를 지연 로딩(Lazy Loading)합니다.
- **오프라인 큐**: `offlineQueue.js`를 통해 네트워크가 끊긴 상태에서도 입력이 가능하며, `window.online` 이벤트 발생 시 서버로 일괄 전송합니다.

> **[Claude] 데이터 동기화 - 보고서 누락 항목:**
>
> **① 오프라인 큐가 실제로 두 개 존재**  
> - `offlineQueue.js` (`QUEUE_KEY`): KV 데이터(plan, fixed 등) 전용. 동일 키가 들어오면 최신으로 덮어씀(dedup).  
> - `offlineQueue.js` (`TX_QUEUE_KEY`): 단건 tx 삽입 전용. 중복 없이 append-only.  
> 두 큐가 서로 다른 플러시 함수(`flush` vs `flushTxQueue`)로 분리 관리됨. 보고서에 누락.
>
> **② IndexedDB 기반 이중화 큐 (`offlineIDB.js`)**  
> localStorage 기반 큐 외에 IndexedDB 큐도 별도 구현되어 있음 (`App.jsx`가 `idbEnqueue`를 import).  
> Service Worker에서 직접 접근 가능하도록 설계 → 향후 Background Sync 지원이 목적.  
> 그러나 현재는 flush 로직이 App.jsx에 연결되어 있지 않아 **사실상 미완성 상태**. 보고서에 누락.
>
> **③ 채널 중복 구독 방지 (`_channels: Map`)**  
> `db.subscribe()`는 내부 `_channels` Map으로 동일 householdId에 대한 채널 재사용을 보장. HMR 등으로 컴포넌트가 재마운트될 때 중복 구독 방지. 보고서에 누락.
>
> **④ 두 개의 병행 DB 경로 (`household_data` + `transactions` 테이블)**  
> - `household_data`: 키-밸류 blob 저장소. tx는 `tx_YYYY` 키로 배열 통째로 저장.  
> - `transactions`: 정규화된 테이블. 단건 insert/쿼리용.  
> `migrated_to_rdb` 플래그로 1회성 마이그레이션 후 두 경로가 병행 운영됨. **잠재적 데이터 일관성 문제** 존재 — `household_data`의 tx와 `transactions` 테이블이 다른 시점의 데이터를 가리킬 수 있음. 보고서에 누락.
>
> **⑤ SQL 트리거 활용 (`trg_sos_approved`)**  
> SOS 가불 승인(`resolveSos`) 시 Supabase DB 레벨의 SQL 트리거가 자동으로 `transactions` 테이블에 insert함. 비즈니스 로직이 DB 트리거에 있어 코드만으로 전체 흐름 파악이 어려움. 보고서에 누락.
>
> **⑥ Supabase RPC 활용 (원자적 연산)**  
> `get_monthly_total_expenses`, `increment_kid_savings`, `complete_and_reward_mission` 등의 RPC 호출로 서버 사이드 집계 및 원자적 업데이트를 처리. 특히 저금 증감과 미션 완료가 트랜잭션으로 묶여 있음. 보고서에 누락.

## 4. 데이터베이스 스키마 구조 (Inferred)

- `household_data`: 가계부 ID 기반의 키-밸류 저장소. 설정, 위젯 레이아웃, 연도별 tx 데이터 등을 보관.
- `transactions`: 개별 지출 내역을 위한 정규화된 테이블. 통계 및 필터링 쿼리용.
- `sos_requests`: 가불 요청 및 승인 프로세스 관리 테이블.
- `kids_profiles/missions`: 자녀 모드 전용 프로필 및 보상 시스템 테이블.

> **[Claude] DB 스키마 - 추가 관찰:**
>
> **`GLOBAL_SYSTEM` 예약 ID**  
> 버그 리포트는 `household_data` 테이블의 `id = 'GLOBAL_SYSTEM'`에 `bug_${timestamp}_${hid}` 패턴의 키로 저장됨. 일반 가계부 데이터와 같은 테이블 공유. 데이터 볼륨이 커지면 `GLOBAL_SYSTEM` 조회 성능이 저하될 수 있음. 별도 `bug_reports` 테이블 분리를 장기적으로 권장.
>
> **DB 트리거 의존성**  
> `sos_requests.status = 'approved'` 업데이트 시 `trg_sos_approved` 트리거가 `transactions`에 자동 insert. 비즈니스 로직이 코드와 DB에 분산되어 있어 코드 리뷰만으로 전체 동작을 파악하기 어려움. 트리거 존재를 `supabase.js` 주석에 명시한 점은 좋음.
>
> **`migrated_to_rdb` 플래그의 취약성**  
> 마이그레이션 완료 여부를 `household_data`에 boolean 플래그로 기록. 마이그레이션 도중 실패 시 플래그가 저장되지 않아 재시도 가능하지만, `transactions` 테이블에 중복 insert 위험이 있음. `insertTxBatch` 실패 시 경고만 발생하고 플래그는 이후에 저장되는 구조라 부분 성공 상황을 고려해야 함.

## [Claude] 추가 아이디어 (보고서 범위 외)

**A. 연도 전환 시 tx 로딩 UX**  
`loadTxYear`를 통해 이전 연도를 요청할 때 로딩 인디케이터가 없으면 사용자가 데이터가 없다고 오해할 수 있음. 연도 전환 시 Skeleton UI 또는 "불러오는 중..." 표시 권장.

**B. `offlineQueue`와 `offlineIDB` 통합 고려**  
두 큐가 중복 역할을 수행 중. localStorage 큐는 동기식이고 Service Worker 접근이 안 됨. IndexedDB 큐는 비동기지만 현재 미완성. **장기적으로는 IDB 하나로 통합**하고 localStorage 큐는 deprecate하는 방향이 깔끔함.

**C. Supabase Realtime에서 `tx_YYYY` 업데이트 처리**  
`updateSharedState`에서 `tx_YYYY` 키는 해당 연도가 이미 로드된 경우에만 실시간 반영됨. 만약 파트너가 작년 데이터를 수정했는데 현재 사용자가 올해 데이터만 로드했다면 업데이트를 무시함 — 의도적 설계이지만 명시적 주석 또는 로그 추가 권장.
