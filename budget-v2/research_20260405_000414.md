# PLAN_v4 심층 분석 및 구현 로직 리서치 보고서

> **작성일시**: 2026년 04월 05일 00:04:14
> **대상 코드베이스**: `budget-v2` 프로젝트

## 1. 개요 및 분석 배경

본 보고서는 `PLAN_v4.md` 문서와 현재 `budget-v2` 프로젝트 코드베이스를 정밀 분석하여 달성된 최적화 및 버그 수정의 기술적 맥락을 파악하고 향후 아키텍처에 미칠 영향을 검토하기 위해 작성되었습니다. `PLAN_v4`는 초기 로드맵(`v1~v3`)에서 확인된 아키텍처 부채를 걷어내고, UI/UX 품질을 극대화(Premium Look)하기 위한 12가지 주요 과제(P0~P3)를 처리한 내역을 담고 있습니다.

## 2. P0: 크리티컬 버그 수정 상세 리서치

### BUG-01: 라이트 모드 날짜 Picker 색상 파손
*   **원인**: `<input type="date">` 요소에 `colorScheme: "dark"`가 인라인 스타일로 하드코딩되어 있어, 라이트 모드에서도 OS 날짜 Date picker UI가 강제로 다크 모드로 렌더링되었습니다.
*   **해결 로직**:
    *   `InputModal`, `TxEditModal`, `QuickEntrySheet`, `EntryView`에서 하드코딩된 `colorScheme` 제거.
    *   `globalStyles.js` 내에 `:root { color-scheme: dark; }` 및 `.light { color-scheme: light; }`를 선언하여 테마 변경 시 웹뷰/브라우저의 기본 Form 요소들이 자동으로 테마를 따라가도록 개선했습니다.

### BUG-02: `SimulatorView` 슬라이더 설정(sliderCfg) 미연결
*   **원인**: `App.jsx`에서 `BudgetView`를 호출할 때 `sliderCfg`와 `setSliderCfg` props를 전달하지 않아, `BudgetView` 내부의 `SimulatorView`에서 슬라이더 값을 변경해도 전역 상태에 반영되지 않고 초기화되는 현상이 발생했습니다.
*   **해결 로직**: `App.jsx` -> `BudgetView` -> `FixedTab` -> `SimulatorView` 로 이어지는 Props Chain을 구성하여 전역 상태 저장(`savePrivate`)과 연동되도록 조치했습니다.

## 3. P1 & P2: 기능 결함 및 UI/UX 개선 상세 리서치

### BUG-03: `EntryView` 고아 접근성 및 솔로 모드 누락
*   **원인**: 내비게이션(Nav)에서 `QuickEntry(BottomSheet)` 구조로 개편된 후 기존 `EntryView`로 진입할 방법이 없었으며, `plan` 상태를 주입받지 않아 '솔로 모드'인지 여부를 판별하지 못해 남편/와이프 선택 UI가 무조건 노출되는 문제가 존재했습니다.
*   **해결 로직**: `App.jsx`에서 `EntryView`에 `plan` 객체를 명시적으로 전달하도록 수정하고, 뷰 내부에서는 `!plan?.isSolo` 조건부 렌더링을 적용해 가시성을 제어하였습니다.

### UX-01: 올드스쿨 테마 FAB 버튼 오염 방어
*   **원인**: 올드스쿨(Win 3.1) 테마용 CSS Selector가 모든 `button` 태그에 테두리(border)와 배경색을 입히면서 둥근 형태의 FAB 버튼 디자인을 파괴했습니다.
*   **해결 로직**: 예외 처리가 작동되도록 `Nav.jsx`의 FAB 버튼에 `className="fab"`를 추가하고, CSS를 `.oldschool button:not(.fab)`로 구체화했습니다.

### UX-02: 라이트 배경 카드 텍스트 가독성 최적화
*   **원인**: 사용자가 커스텀 카드의 색상을 밝게 설정할 경우 텍스트 마저 흰색(`#fff`)으로 지정되어 글씨를 읽을 수 없었습니다.
*   **해결 로직**: `helpers.js`에 배경색의 상대 휘도를 계산하는 `getContrastText` 함수(W3C WCAG 권고 알고리즘 기반)를 도입하여 배경 밝기에 따라 텍스트가 흑/백으로 자동 토글되도록 처리했습니다.

## 4. 아키텍처 및 성능 최적화 관점 (Phase 2, 3, 4 기반)

`PLAN_v4` 이전에 진행된 `v2~v3` 아키텍처 개선사항들과 융합된 코드 구조를 앱의 핵심 `App.jsx`에서 다음과 같이 확인하였습니다.

### 4.1. 단일 진실 공급원 (Single Source of Truth)
*   **적용**: 불필요한 `plan.monthlyIncome` 필드를 걷어내고 `plan.salary` (husband/wife)로 통합하여 데이터 마이그레이션을 1회성으로 수행하는 로직이 적용되어 데이터 정합성을 확보했습니다.

### 4.2. 트랜잭션(`tx`)Lazy Loading 및 연도별 관리
*   **전략 로직**: 
    1. 단일 JSON 배열로 저장되던 `tx`를 `tx_YYYY` 형태의 키 매핑으로 연도별 분리를 수행합니다.
    2. 로드 시점에서는 `getYear()`로 현재 연도의 내역만 초기 로딩하고, `loadedTxYears` Set 컨테이너를 통해 중복 로드를 방지합니다. 
    3. 과거 내역 조회 시에만 `loadTxYear(year)`를 비동기로 호출하도록 개선하여 수백~수천건의 데이터로 인한 메모리 증가와 버벅임을 차단했습니다.

### 4.3. SetShared 래퍼 기반 동기화 및 오프라인 큐 (Offline Queue)
*   모든 상태 쓰기가 `setShared`를 통과하도록 만들었으며, 여기서 가장 눈여겨 볼 점은 다음 3가지입니다.
    *   **낙관적 업데이트(Optimistic Update)**: `rawSetter` 호출을 통해 UI를 즉각 반응시킵니다.
    *   **데이터 검증(Validation)**: `validate(key, value)` 레이어를 둬서 손상된 데이터 저장을 방지.
    *   **Fallback**: 네트워크 오프라인 시 `offlineQueue.js`에 트랜잭션을 담고 `window.addEventListener('online', ...)` 이벤트를 통해 연결 회복 즉시 밀린 데이터를 동기화합니다.

## 5. 결론 및 다음 단계 제언

`PLAN_v4`에 기록된 12가지 이슈 패치는 단순한 뷰 수정에 그치지 않고, 시스템 전반의 횡단 관심사(스타일 오케스트레이션 및 상태 전파)를 말끔히 정리했습니다. 이제 앱은 매우 높은 일관성과 안정성을 담보하게 되었습니다. 

**다음 단계(Next Step) 제언:**
*   **아키텍처 확장**: 현재 `tx` 연도별 파티셔닝 전략 도입이 확인되었으므로, 향후 Calendar나 Report 뷰에서 발생할 수 있는 캐싱 교착상태(`Stale state`)를 관리하기 위한 React Query 또는 SWR 과 같은 Caching 레이어 도입을 고려해 볼 만합니다.
*   **컴포넌트 독립성**: `BudgetView`의 `sliderCfg` Props Drilling 현상을 볼 때, `BudgetContext` 의존성을 높여 최하단 뷰 컴포넌트까지 Context 값으로 바로 연결되게 하는 리팩토링이 효과적일 것입니다.
